# 跨平台换行与生成数据校验

Windows 上已审译文在 Linux WebTiles 中大量回退英文的原因，是依赖校验曾直接对文件字节计算 SHA-256。Windows 自动生成的头文件含 CRLF，Linux 生成的是 LF；即使代码含义相同，也会被视为审核后发生变化。

现在 UI 和 TextDB 共用 `tools/localization/source_hash.py`：计算依赖摘要前只将 CRLF 转为 LF。实际代码、空格、编码及单独的 CR 变化仍会使校验失败，保留整句英文回退。新增依赖记录也应使用该函数计算摘要。

四个数据生成器明确输出 UTF-8／LF，种族标志位排序后再拼接，避免 Python 集合遍历顺序使生成文件因进程而不同。排序仅改变按位或表达式的书写顺序；所有标志位集合保持不变。仓库通过 `.gitattributes` 指定文本使用 LF，不对整个上游仓库进行无关的格式重写。

现有依赖记录只在匹配修复前已知文件摘要时迁移；历史上已经失效的记录不借此放行。没有修改英文原文、译文正文或审核状态。

服务器拉取 `stone_soup-0.34.1-zh` 后，需要重新构建 WebTiles 并启动新的游戏进程。使用服务器原有的 `make WEBTILES=y` 构建参数即可；新增的工具依赖会触发目录重建。已运行的游戏进程仍使用旧二进制中的翻译目录。

验证结果见 [检查记录](lf-portability-01-checks.json)。本地验证覆盖完整 UI／TextDB 在模拟 LF、CRLF 依赖文件下的导出一致性，以及真实源码变化后的英文回退；不代替服务器上的 Linux 编译和运行验收。
